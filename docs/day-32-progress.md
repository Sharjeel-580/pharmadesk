## What changed

### Part A — Restore semantics decided (D169, option (a))

- **Decision:** restore stays exactly as D150 built it — upsert-by-id only, never deleting — and the limits are now stated in plain language on the backup screen (a new "What restore does NOT do" card) and in the restore confirm dialog, instead of extending restore to cover counters + sale-payment legs. The extension cannot be tested end-to-end here (payment legs live only in a Firestore subcollection; rewriting them on restore is a Firestore-only money-path change with no live project to verify it against — a Dazy-only step), and an unverified rewrite of payment records is worse than stating the limit.
- **Verified semantics (pinned by test):** restore only adds or replaces — a record created after the export survives untouched; an edited record reverts to the backup value. Counters are NOT restored (the export deliberately has NO `counters` / `inventoryCounters` section; derived `computeDailyCounters` follows the restored records — importing a sale moves today's counter by exactly Rs 10,000.00). Sale payment legs are NOT restored on Firestore (no `salePayments` section; the sale returns with total, method and cash received); in the mock the legs DO round-trip because `Sale.toMap` carries them inside the sale doc.
- **Brief §7 wording correction (flagged, not papered over):** the brief's parenthetical "records deleted after export do not come back" is wrong under D150 upsert-by-id — a doc that IS in the backup IS re-created on import (proved: importing an export into a fresh layer creates the missing sale). What restore never does is DELETE a live record. The screen and dialog now say this plainly, and the old "replaces the current live data" wording — which overpromised a rollback — is gone. (The repos expose no delete API and the ledgers are append-only, so deletion is barely a live operation in the demo.)
- **Cross-backend edge (Day 24, documented, NOT fixed):** a mock-export sale doc id differs from its idempotency key (mock assigns `sale-DHA-1001`, the key is `sale-<branch>-<millis>`) — pinned by test. Same-backend round-trips are unaffected. A mock export restored into Firestore writes the sale doc under the exported id, breaching the D53 / rules invariant (doc id = idempotency key). Fixing it would re-key the restore by idempotencyKey, changing restore identity and ImportReport counting, and cannot be verified end-to-end without a live project — deferred as a follow-up.

### Part B — Phase 8 QA depth (D170)

- **Route walk:** the same 47 shell routes as Day 27 — Week 6 added no routes (brief §1–§7 are guards, keys, model fields and restore text on existing screens) — re-walked with the count asserted (`hasLength(47)`), no placeholders, no 404s.
- **The sweep harness was undercounting (found and proved this day):** the D160 helper drains `tester.takeException()` and counts "RenderFlex overflowed". When two overflows arrive in one pump without an acknowledgement in between, the binding collapses them into a single `"Multiple exceptions (2)..."` string containing no "RenderFlex overflowed" — so the D160 count reads **0 for a screen that really overflowed twice**. Proof: the supplier detail screen (2 real overflows) counted 0 the D160 way. The Day 32 sweep uses a `FlutterError.onError` trap (`_OverflowTrap` in the day test): it records each error as the handler sees it, forwards to the binding's handler, and counts DISTINCT messages (the same overflow is re-reported on every pump that lays it out again — the cashbook dialog read 4 raw reports for one overflow). A synthetic two-overflow test pins the difference (D160 drain 0, trap 2). **Consequence for earlier claims:** the Day 27 "0 overflows" figures were measured with the undercounting drain — any Day 27 screen that overflowed twice in one pump would have passed spuriously. The D160 screen list is re-run this day with the corrected counter (all pass); the coordinator should treat the D160 figures as "no single-overflow found", not as a proof of zero.
